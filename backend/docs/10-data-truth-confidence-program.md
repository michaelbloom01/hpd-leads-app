# Data Truth & Confidence Program

## Product Standard

Double Edge should not treat a lead row as truth. A lead is a workflow view over canonical entities, buildings, contacts, relationships, and claims. For any relationship the system should answer:

- What do we believe?
- Why do we believe it?
- Which sources support it?
- Which sources contradict it?
- How fresh is the evidence?
- How confident are we?
- What action is safe to take?

## Additive Architecture

The program is additive to the existing PostgreSQL model:

- `leads` remains the CRM/workflow row for pipeline, notes, follow-ups, and outreach history.
- `canonical_entities`, aliases, memberships, building links, and proposals remain the identity graph.
- New truth tables store explainable claims, evidence, confidence snapshots, review items, validation runs, and golden cases.

Primary new tables:

| Table | Purpose |
|-------|---------|
| `truth_claims` | Normalized facts such as entity identity, building management, ownership, contactability, and source-derived assertions |
| `truth_evidence` | Per-claim source observations, support/contradiction status, source quality, observed date, and raw payload |
| `confidence_snapshots` | Computed confidence/actionability state for a lead, canonical entity, building, or contact scope |
| `truth_review_items` | Human-review queue entries with proposed change, support, contradiction, rationale, run ID, and review status |
| `golden_verification_cases` | Benchmark cases for hard NYC property-identity patterns |
| `truth_validation_runs` | Auditable validation-job envelopes with dry-run status, metrics, samples, and rollback strategy |

## Confidence Rules

`src/services/confidence.py` implements deterministic first-pass scoring. It explicitly weights:

- Source quality: outreach confirmation, HPD contacts, HPD registrations, building links, NY DOS, company websites, Google/Maps profiles, ACRIS, PLUTO, web crawl, legacy lead snapshots.
- Agreement: independent supporting sources increase confidence.
- Disagreement: contradicting sources sharply reduce confidence and block diligence-grade action.
- Freshness: stale records are downgraded even if the source is otherwise good.
- Claim risk: ownership, registered agent, management, contact, and identity claims have different risk penalties.

Every computed claim rationale and materialized confidence snapshot carries a `confidence_policy_version`, and the truth dashboard actionability rules expose the same version. This makes later scoring-rule changes auditable against older claim/snapshot outputs instead of silently changing the interpretation of stored confidence. The current policy is `truth-confidence-v2`: source names are deduped before quality scoring, and source quality is anchored on the strongest distinct independent support paths. Additional lower-quality support can still help through agreement/evidence counts, but it does not drag down a fact that also has stronger role-explicit evidence. This fixes the earlier calibration issue where duplicate same-source rows could inflate quality while real distinct source bundles were under-credited.

Actionability levels:

| Level | Required posture |
|-------|------------------|
| `broad_discovery` | Useful for exploratory search only; requires at least one supporting source and evidence item |
| `ranked_sourcing` | Good enough to rank and compare, but not final outreach; requires at least one supporting source and evidence item |
| `automated_enrichment` | Safe for non-destructive automated enrichment or source refresh, but not outreach; requires at least one supporting source and evidence item |
| `recommended_outreach` | Good enough for human-reviewed outreach; requires at least one supporting source and evidence item |
| `acquisition_quality_diligence` | Strong enough for diligence or investment judgment; requires at least two supporting sources and evidence items |
| `do_not_act` | Too stale, conflicted, or weak |

The actionability gate is stricter than the confidence score alone. A high score with no explicit supporting source/evidence count still returns `do_not_act`; diligence-grade action also requires two independent support paths, no contradictions, and fresh evidence. Subject summaries preserve that block: if every claim is `do_not_act`, the rolled-up `safe_actions` remains `do_not_act` instead of falling back to `broad_discovery`. Human-review proposals follow the same rule: unsafe canonical match proposals stay non-actionable until a reviewer decides what to do with them.

The truth dashboard returns this threshold ladder even while the additive truth schema is still gated. Settings can therefore show what the product is allowed to do before claim tables exist, instead of hiding the safety standard behind an empty dashboard.

## Claim Ledger

`GET /api/v1/truth/leads/{lead_id}/summary` returns a lead-level read model that combines:

- Synthetic claims inferred from current live tables, such as current building links, contact path, and canonical membership.
- Existing truth-bearing outreach outcomes inferred as read-only support or contradiction evidence before ledger materialization.
- Persisted claims from `truth_claims` and aggregated `truth_evidence`.
- Overall confidence, contradiction count, safe actions, and review bucket.

This lets the UI expose an evidence-backed answer before every source has been migrated into the claim ledger.

The summary response makes the core trust questions explicit, not just implicit in the claim rows. `belief_summary`
includes `what_we_believe`, `why_we_believe`, rolled-up `supporting_sources`, rolled-up `contradicting_sources`,
`freshness_days`, `safe_actions`, and the contradiction count. Claim rows still carry the detailed predicate,
confidence score, evidence counts, source arrays, and rationale.

`GET /api/v1/truth/subjects/{subject_type}/{subject_id}/summary` generalizes the same read model for `lead`, `canonical_entity`, `entity`, `building`, `contact`, `hpd_contact`, and `person` subjects. For non-lead subjects it reads both subject-side and object-side claim ledger entries, so a building can show ownership/management/contact claims and an entity can show building/contact relationships without being forced through a lead row. Building subjects also synthesize read-only current-table claims from `buildings`, `building_management`, and `building_contacts`; this keeps Building Detail useful before persisted ledger claims exist. Contact subjects resolve public `contact/{id}` and internal `hpd_contact/{id}` IDs to HPD contact role, mailing-address, and building-link evidence, then layer in persisted `hpd_contact` ledger claims after materialization. Canonical/entity subjects synthesize identity, alias, lead-membership, building-membership, and open-proposal claims from the canonical tables, including contradiction evidence when memberships are weak/candidate-only or proposals are not safe to execute. Person subjects resolve normalized HPD officer/contact names and enrichment owner-principal observations, and they flag same-name/multiple-address ambiguity as contradiction evidence because Double Edge does not yet have a durable person identity table. Lead, building, entity, contact, and person summaries also inspect existing outreach feedback for truth-bearing outcomes, so "does not manage," bad contact paths, confirmed managers, confirmed decision-makers, and referrals affect confidence/actionability before persisted ledger materialization. When the truth schema is not yet migrated in a target environment, the endpoint returns the available current-table building/contact/canonical/person/outreach evidence plus a schema-gated status instead of pretending persisted claim-ledger truth exists.

Lead and building contact views also apply deterministic safe-action labels to HPD/DOS contact records. These labels distinguish board/owner research paths, possible manager paths, legal or mailing paths, stale evidence, and records that need role review, so source contact evidence does not masquerade as a verified outreach-ready PM contact.

`POST /api/v1/truth/materialize/preview` previews the next ledger backfill without changing data. It counts planned claims from:

- `building_management` current building-manager links
- role-specific HPD-contact-to-lead building links when HPD contact role, building-management role, BBL, and strict verification identity key all agree
- `building_contacts` HPD contact roles, including ownership, management-company, registered-agent, and person/officer associations
- `building_contacts` HPD mailing addresses as separate address claims
- `enrichment_results` source-specific phone, email, website, and owner-principal observations
- `leads` contact-path fields
- `canonical_entity_leads` memberships
- `acris_transactions` recorded-property transaction observations
- `dob_permits` permit-activity observations
- `hpd_complaints`, `hpd_violations`, `hpd_litigation`, `emergency_repairs`, `aep_designations`, `eviction_filings`, `energy_grades`, and `facade_inspections` building condition, distress, litigation, and compliance signals
- `pad_addresses` building reference and BIN/BBL crosswalk observations
- `outreach_events` truth-bearing lead, building, canonical-entity, and target-list operator feedback such as bounces, wrong numbers, bad emails, "does not manage" replies, confirmed managers, confirmed decision-makers, and referrals

Preview responses include raw representative source rows plus `sample_materialized_claim_specs`, a bounded, source-diverse sample built by the same claim/evidence builders used in execute mode. Each sample spec includes stable `claim_id` and `evidence_id`, subject/object IDs, predicate, normalized value, claim type, source record, observed date, confidence, freshness, actionability, and support/contradiction status. Operators should review this field before approving execute mode; it is the dry-run proof of what ledger rows would be upserted.

Materialization preview and execution can be source-scoped with repeated `source` query parameters, such as `POST /api/v1/truth/materialize/preview?limit=50&source=building_management&source=outreach_feedback` or `/api/v1/jobs/truth_materialization/start?dry_run=false&confirm_execute=true&limit=50&source=building_management`. Source scoping is the preferred rollout protocol for large ledgers: preview one bounded source batch, inspect sample claim/evidence specs and source counts, execute only that approved batch, then verify the run-specific rollback manifest before moving to the next source. Unsupported source names are rejected instead of silently widening the batch.

The `truth_materialization` job uses the same service. It defaults to dry-run mode. Execute mode requires `confirm_execute=true` and only upserts `truth_claims`, `truth_evidence`, and derived `confidence_snapshots` using stable IDs; it does not change leads, buildings, canonical entities, or relationship tables. Execute-mode results include selected source filters, before/after truth table counts, upsert counts, confidence snapshot counts, skipped count, conflict samples, source counts, run ID, rollback instructions, and a rollback-manifest summary. The task stores run metrics in `truth_validation_runs`.

Because execute mode uses stable-ID upserts, rollback reporting distinguishes rows created by the run from rows that already existed and were updated. Revision `010_truth_manifest` adds `truth_materialization_manifest`, which stores every claim/evidence/snapshot ID touched by a run, whether it was new, and before-snapshot JSON for rows that already existed. New claim/evidence/snapshot rows can be deleted by run ID in dependency order with `scripts/truth_materialization_rollback.py`. Updated rows include before snapshots for targeted repair, but broad rollback of updated rows should still use backup or point-in-time recovery rather than blindly deleting stable IDs.

Signal-source materialization is deliberately phrased as source-observation claims, not final operating truth. For example, an ACRIS row becomes a `property_transaction` claim on a building, a DOB row becomes `permit_activity`, and HPD violation/litigation/distress rows become building condition or distress signals. These observations support sourcing and diligence confidence, but they do not by themselves assert that a lead owns or manages a building.

The HPD-contact-to-lead bridge is intentionally role-specific. It emits lead/building claims only when the HPD contact role, the current `building_management.role`, the BBL, and a strict verification identity key all agree. The strict key strips legal suffixes such as LLC/Inc but preserves business-role words such as `PROPERTY MANAGEMENT`, so a broad dedupe key like `HARLEM` cannot verify `HARLEM PROPERTY MANAGEMENT`. `ManagementCompany` can support `manages_building`; `Agent` can support `registered_agent_for_building`; `CorporateOwner` can support ownership; `HeadOfficer` and `SiteManager` remain their own contact-role evidence. `Agent` contacts are not promoted into manager verification, because conflating registered-agent and operating-manager roles would create false confidence.

`backend/scripts/truth_live_hpd_role_audit.py` makes that boundary repeatable against official NYC Open Data or downloaded extracts. It now exposes current role-specific HPD claim previews with predicate, claim type, source record ID, strict identity keys, and `can_support_management_claim` instead of only returning aggregate counts. A June 1, 2026 live read-only run over the 14 built-in operator/HPM targets matched `14/14` registrations, found `13` current registrations, emitted `58` current role-specific claim previews, and found `13` strict HPD `Agent` identity matches after legal-suffix stripping. It found `0` `ManagementCompany` rows and `0` source-evidence intake candidates, so the official HPD slice is usable as role-specific Agent/SiteManager/owner/officer evidence but still does not supply manager-proof support for `manages_building`.

The HPD acquisition packet also exposes NYC Open Data view `v4vh-sni9`, titled `Property Managers-1st Step`, as registration lookup context only. Despite the title, the live view exposes registration/address/block/lot/date fields and no manager, agent, contact-type, corporation-name, or role-specific management fields. It can help locate RegistrationID rows before querying `feu5-w2e2` Registration Contacts, but it cannot support, contradict, verify, or activate a `manages_building` claim unless a matching `ManagementCompany` contact row or another exact manager-proof source is reviewed.

Outreach-feedback materialization is different because a human response can directly support or contradict a relationship. The backfill path converts only truth-bearing outreach outcomes into claims, preserves the best available subject context (`lead`, `building`, `canonical_entity`, or `target_item`), uses the same stable IDs as live outreach writes, and marks contradicting evidence with negative evidence weight plus `do_not_act` actionability so a "we do not manage that" reply overrides stale source assumptions.

Live outreach logging has an additional schema gate. Lead, building, and unified outreach endpoints first check whether the truth tables exist and Alembic is at `010_truth_manifest`; if not, they still save the outreach event and return a `truth_claim_status` explaining why claim-ledger writes were skipped. This keeps operator feedback capture working in environments where the additive truth migration has not yet been applied.

Outreach feedback uses predicates that describe whether a safe operating path remains valid: `has_valid_contact_path`, `has_valid_management_relationship`, and `has_referral_path`. In particular, "does not manage" and manager confirmation replies materialize as `has_valid_management_relationship`, while generic current-table lead/building summaries may still use broader relationship predicates such as `manages_buildings`.

After confirmed materialization, the job computes `confidence_snapshots` grouped by subject. These snapshots provide a compact per-lead, per-building, per-contact, or per-entity trust posture from the underlying claims: aggregate confidence, actionability, supporting claim count, contradiction count, stale claim count, run ID, and the claim IDs/types that explain the score.

`GET /api/v1/truth/adjudication-preview` and `backend/scripts/truth_adjudication_preview.py` provide the next read-only gate after materialization. The adjudicator groups equivalent claim facts by subject, predicate, object, and normalized value, recomputes support/contradiction/freshness confidence, and reports whether any fact is safe to mark verified. A fact is only a verification candidate when it has at least two independent supporting sources, at least two supporting evidence rows, no contradictions, fresh evidence, and a verified-level recomputed confidence score. The preview returns blocker counts such as `needs_independent_source`, `needs_additional_evidence`, `stale_evidence`, `contradicting_evidence`, and `confidence_below_verified_threshold`; it always returns `dry_run=true` and `mutations_planned=0`.

The same preview also reports sampled source-overlap coverage, ledger-wide source overlap, a narrow role-source-overlap pilot, a scaled role-source-overlap scan, a manager-source bridge preview, a manager external-source acquisition preview, a post-materialization role-overlap simulation, a role-overlap activation plan, a stale role-claim correction preview, a read-only verification gap plan, and a separate verified-confidence gap plan. The verification gap plan proposes evidence-acquisition sources and manual-evidence payload templates for single-source fact groups, but it is not evidence and cannot mark a claim verified by itself; for `manages_building` it now asks for HPD `ManagementCompany`, company website, outreach-confirmed, NY DOS, or NY DPS order-entry evidence rather than generic HPD contacts. The verified-confidence gap plan covers fact groups that already have enough independent sources and evidence but still fall below the 0.90 verified threshold, exposing the score gap, average source quality, current source mix, stronger role-explicit source families, one-source upgrade simulations, and suggested-bundle simulations before a reviewer can mark the fact verified. These simulations are read-only: they add hypothetical support to the confidence model, keep the current lower-quality source mix in the fact group, do not lower thresholds, and do not record evidence. Bundle simulations are explicitly acquisition-only (`acquisition_required=true`, `recording_ready=false`) and list the real evidence fields needed before any manual-evidence execution can be considered.

It reports current ledger source overlap, source-ready facts that remain below the verified confidence threshold, single-source gaps, HPM next-source seeds, and operator-confirmed second-source seeds in one read-only payload. ### Manual Evidence Capture

`POST /api/v1/truth/manual-evidence` and `backend/scripts/truth_manual_evidence.py` provide the operator path for reviewed evidence that does not come from a bulk public-data ingest. This is how a reviewed company website, NY DOS lookup, Google/Maps business profile, broker call, bounced email, wrong-manager response, or confirmed manager can enter the same claim/evidence ledger without being mislabeled as HPD truth. The request records the subject, predicate, object, claim type, normalized value, support status (`supports` or `contradicts`), source name, source record or URL, observed date, note, and recorder. It computes confidence/actionability with the same policy version as materialized claims, creates stable claim/evidence IDs, and builds a confidence snapshot.

Manual evidence is preview-first. A default request returns `dry_run=true`, `allowed_execute=false`, planned claim/evidence/snapshot upserts, rollback manifest entries, and required execute parameters. Execution requires `dry_run=false&confirm_execute=true` (or `--execute --confirm-execute` in the CLI). The CLI accepts `--payload-file` for a reviewed manual-evidence payload or source-evidence intake preview, so approved evidence can be replayed from the exact preview artifact instead of retyped. If the payload file is a source-evidence batch preview, the CLI extracts only ready candidates that add a new supporting source and leaves duplicate/freshness-only or contradiction rows for separate review. Multi-payload replay requires the extra `--confirm-batch-execute` flag in addition to `--execute --confirm-execute`, because it may write more than one claim/evidence/snapshot bundle. Source-evidence batch previews expose the same boundary in `manual_evidence_replay_boundary` and `recommended_recording_scope.required_execute_flags_for_batch`, so the approval-prep preview and replay CLI use the same three-flag contract. Manual-evidence batch previews also include `post_execution_expectations`: rerun adjudication, post-recording proof, truth health, and runtime completion audit; keep verified single-source claims at zero; and keep source refresh, relationship materialization, automatic verified-status changes, and business-use activation out of the evidence-write path. Rollback uses the same `truth_materialization_manifest` protocol: new rows can be deleted by run ID in dependency order, while updated rows carry before-snapshot audit samples and require backup/PITR or targeted restore.

## Review Workflow

`GET /api/v1/truth/review-queue` combines:

- Explicit `truth_review_items`
- Existing canonical entity match proposals

Queue names include:

- `safe_auto_accept`
- `suggested_merge`
- `needs_human_review`
- `conflicting_evidence`
- `insufficient_evidence`
- `do_not_merge`

The queue is designed to show the proposed change, supporting evidence, contradicting evidence, confidence, and what database change would happen before anything mutates data.

`POST /api/v1/truth/review-queue/{review_id}/decision` adds the decision layer. It accepts `approve`, `reject`, `needs_more_evidence`, and `do_not_merge`, and defaults to `dry_run=true`. Dry-run responses include previous state, resulting state, decision audit payload, target status, reviewer, evidence context, proposed database changes, and rollback strategy. Execution requires `confirm_execute=true` and is currently limited to `truth_review_items` status transitions; canonical entity merge proposals remain preview-only in this endpoint so broad/risky merges cannot be applied accidentally. Approval is also blocked for conflicting-evidence, insufficient-evidence, do-not-merge, or `do_not_act` review items, so a reviewer can reject, defer, or mark do-not-merge without accidentally turning a warning queue into an approval path. Confirmed decisions append both the previous and resulting review state into the item rationale, so restoring a mistaken status decision does not depend only on external logs.

The `truth_validation` job now bridges adversarial validation into human review. Dry-run validation returns proposed review-item payloads without opening a write session or mutating `truth_review_items` / `truth_validation_runs`. Execute mode requires `dry_run=false&confirm_execute=true` and upserts only `truth_review_items` generated from sampled validation findings; it does not change leads, buildings, claims, or canonical links. Run-level rollback is available through `python scripts/truth_validation_rollback.py --run-id <run_id>`, which defaults to deleting only still-open review items and preserving reviewed decisions unless `--include-reviewed` is explicitly supplied.

## Outreach Feedback Loop

Outreach outcomes now create claim-ledger evidence when the outcome carries truth value:

- `does_not_manage`, `wrong_manager`, and `not_the_manager` contradict a management claim.
- `spoke_with_contact`, `meeting_scheduled`, and `confirmed_decision_maker` support a valid contact-path claim.

- Buildings with multiple current role links

- Leads whose DOS status is not active/current/good standing

## Truth Health Report

`GET /api/v1/truth/schema-status` checks whether the additive truth-confidence tables are present before any business trust is inferred. It reports the expected Alembic revision, current revision, revision status, required table map, missing tables, and `mutations_planned=0`. Readiness is table-based so future Alembic revisions do not accidentally hide an already-present truth schema; revision drift is still reported as diagnostic evidence.

`GET /api/v1/truth/health-report` and `backend/scripts/truth_health_report.py` combine schema readiness, the dashboard, claim-ledger materialization preview, claim adjudication preview, adversarial validation preview, and golden-set benchmark into one read-only trust-gap report. The report is deliberately conservative: any missing truth table, unmaterialized evidence, no safely adjudicable verified claims, active validation issue, weak golden-set coverage, large review queue, conflict ratio above threshold, or truth-schema revision drift is surfaced as a gap instead of letting a green build masquerade as data readiness. If the truth tables exist but Alembic is not at the expected truth-confidence revision, the report includes a `schema_revision` trust gap and keeps the activation checklist on `approval_required`.

`GET /api/v1/truth/activation-packet` turns the health report into a compact operator approval packet for the Settings Data Health panel. It returns the verdict, business-use allowed/blocked state, schema revision, missing tables, approval-required steps, source-refresh counts, the first approval-gated source refresh jobs with source names/statuses, golden-case counts, claim-readiness counts, trust-gap summary, next safe commands, and rollback preview command without running Alembic or mutating data. The next-step sequence explicitly separates preview, evidence review, and execution: operators must inspect `sample_materialized_claim_specs`, validation checks, the review queue, golden benchmark, and rollback plan before using the `confirm_execute=true` materialization endpoint. It also separates source-refresh review from source-refresh execution: operators must inspect `source_refresh.next_jobs`, blocked/manual gaps, and source ages before running any approved refresh endpoint with `confirm_execute=true`. The Settings Data Health panel also calls the materialization preview and shows the first stable claim/evidence specs so approval review can inspect concrete predicates, sources, confidence, freshness, actionability, IDs, and support/contradiction status in the UI. The CLI script `backend/scripts/truth_activation_packet.py` returns the same packet shape after also generating the offline Alembic SQL/rollback preflight.

The activation packet now also carries a read-only `verification_frontier` summary derived from adjudication. It keeps the business-use blocker tied to live evidence posture by showing current ledger overlap, verification-candidate count, source-ready facts still below the verified threshold, remaining single-source gaps, HPM/operator next-source seed counts, and the exact `truth_verification_frontier.py` preview command. This prevents an activation failure from looking like a vague framework issue when the real blocker is still verified-claim evidence acquisition.

The report also returns a machine-readable `activation_checklist`. This checklist turns the posture into explicit gates: apply the truth schema, run materialization dry-run, review truth outputs, execute materialization only after approval, refresh or manually record source evidence, and keep business use blocked until the trust gates clear. Each item has a status, reason, approval flag, and planned mutation count so the UI can show the exact next safe action without mutating data. Schema activation counts missing truth tables when tables are absent; revision-drift states report zero planned table mutations and tell the operator to inspect migration lineage instead of blindly creating tables. The final `allow_business_use` checklist row now requires non-`not_ready` posture, zero critical/high gaps, materialized claims, at least one verified claim, no refreshable source jobs, no blocked source jobs, and no manually tracked source evidence gaps. The activation packet applies the same stricter posture and only allows business use when every checklist step is complete, the ledger has materialized claims plus at least one verified claim, no critical/high gaps remain, source refresh has no approval-required, blocked, or manually tracked gaps, and the health report has no trust gaps; a hand-built or partial checklist cannot greenlight an empty ledger. The packet exposes a `claim_readiness` block with claim, verified-claim, and critical/high-gap counts so this decision is inspectable. The positive path is explicit too: when every gate is complete, trust posture is not `not_ready`, verified claim evidence exists, and source/trust gaps are clean, the packet returns `ready_for_business_use`. Once claims already exist and dry-run materialization reports no pending claim work, the materialization dry-run and execute checklist steps can move to `complete` instead of staying permanently approval-required.

Truth APIs, jobs, and activation-checklist guidance use the same current-schema predicate. Persisted truth dashboard reads, persisted claim inclusion in summaries, review queues, review decisions, validation preview, materialization preview, `truth_validation` jobs, and `truth_materialization` jobs are blocked unless the truth tables exist and Alembic is at the expected truth-confidence revision. The checklist also keeps materialization dry-run, output review, and execute steps blocked in revision-drift states. This prevents a partial/manual table state or future revision drift from being treated as safe for ledger-backed workflows.

When the truth schema is not ready, the health report still includes the read-only seed golden benchmark and configured/evaluable case counts. It does not score live claims or mark the product ready; it simply keeps benchmark coverage visible while the ledger migration remains pending in that environment. In the active local DB, schema is ready but the same not-ready posture remains until materialized and verified claims exist.

The report also includes the canonical source audit used by the Settings data-health surface. This keeps source readiness visible even when the truth ledger schema is not yet migrated: HPD registrations, HPD contacts, PLUTO, ACRIS, DOB, litigation, emergency repairs, AEP, evictions, energy, facade, PAD, coordinates, NY DOS cache, Google Places, Hunter, company website/web crawl enrichment, and outreach feedback each report whether their table exists, whether the surface is wired, whether recent evidence exists, whether the latest evidence is stale, and the last observed volume.

The source audit also returns a no-mutation source refresh plan. It groups stale or missing evidence by job type, marks blocked jobs such as missing schema or unwired sources, and keeps `approval_required=true` with `safe_to_run_automatically=false`. Actual ingestion refreshes mutate source tables and data-quality logs, so the plan is advisory only until Michael explicitly approves a run. Non-refreshable evidence streams, such as outreach feedback, remain visible in source gaps without inventing a background refresh job.

The job API now enforces the same approval boundary for public-data source refreshes and other mutation-capable background jobs. Source jobs such as HPD registrations, HPD complaints, HPD violations, ACRIS, DOB permits, litigation, emergency repairs, AEP, evictions, energy grades, facade inspections, PAD, and coordinate backfill default to an `approval_required` preview response and do not create an `ingestion_jobs` row. So do enrichment, scoring, smart-list evaluation, quality checks, lead generation, entity resolution, and lead reconciliation starts. Execution requires `dry_run=false&confirm_execute=true`, which makes the approval state explicit in the job config before any source table, score field, generated lead, quality log, enrichment result, or job output can be changed.

Compute-heavy reconciliation outputs are designed to be auditable, not magical. Entity-resolution dry-runs carry a run ID, guardrails, and sampled clusters in both the return payload and stored job config. Execute mode is limited to approved `safe_keep` clusters, records rollback samples for changed portfolio/link counts, and keeps review-required, unresolved, and retire buckets outside the auto-write path.

HPD building ingestion no longer auto-cascades into scoring, lead generation, or coordinate backfill after completion. Those follow-up jobs are still useful, but they must be started as their own approval-reviewed jobs so a single source refresh cannot quietly trigger additional local data mutations.

Selected-lead enrichment follows the same pattern. The batch endpoint validates the selected lead IDs and returns an approval preview by default; it only creates an enrichment job when called with `dry_run=false` and `confirm_execute=true`.

Single-lead enrichment is also preview-first. `POST /api/leads/{lead_id}/enrich-all` reads the current lead row and returns an approval preview by default, including the exact execute query; the contact/search/scrape/AI enrichment workflow only runs with `dry_run=false&confirm_execute=true`.

The report always returns `dry_run=true`, `mutations_planned=0`, a threshold block, summary posture, trust gaps, activation checklist, source audit status, and the underlying dashboard/preview/benchmark payloads used to reach that posture.

## Safety Contract

Production/local mutations remain gated:

- Dry-run previews first.
- Explicit approval before mutating local or production data.
- Every batch run needs a run ID, before/after counts, sample findings, skipped records, conflicts, confidence snapshot counts, and rollback strategy where feasible.
- Broad auto-merge is never allowed for review-required, conflicting, or multi-base-name groups.
